# کاهش مصرف مرورگرهای سرور — ۲۰۲۶-۱۰-۲۹

سرور ۴ vCPU و حدود ۹٫۷ GiB RAM دارد و چندین سرویس دیگر روی آن فعال‌اند.
پیش از تغییر، vmstat در دو نمونه ۹۵–۹۶٪ CPU مشغول نشان داد؛ مصرف کل میزبان
را نباید به کانتینر AI Studio نسبت داد. دو کانتینر مرورگر اینستاگرام نیز در
یک نمونه مجموعاً حدود ۱۳۵٪ CPU مصرف داشتند؛ ۱۰۰٪ Docker برابر یک هسته است.

نمونه‌های کانتینر از `cpu.stat` و `memory.current - inactive_file` خوانده شدند:

| حالت | مرورگرهای باز | working set، MiB | CPU در بازهٔ ۲۰ ثانیه |
| --- | ---: | ---: | ---: |
| پیش از تغییر | ۷ | ۳۰۹۵٫۸ | ۶۹٫۸٪ |
| فلگ‌های منابع و حذف تب خالی | ۷ | ۲۸۳۹٫۳ | ۱۴۸٫۳٪ |
| lazy startup، قبل از بازکردن حساب اضافه | ۲ | ۱۳۶۹٫۷ | ۱۰۸٫۷٪ |
| بعد از بیدارکردن chatgpt2 | ۳ | ۱۸۴۱٫۰ | ۹۱٫۲٪ |
| نسخهٔ نهایی، هر دو default آماده، بدون job فعال | ۲ | ۱۰۱۱٫۳ | ۶۷٫۴٪ |

بازه‌ها workload یکسان ندارند: warm-up، بازیابی و smoke request در نمونه‌های
جدید فعال بودند. این اعداد benchmark کنترل‌شده نیستند و کاهش CPU را اثبات
نمی‌کنند. کاهش RAM عمدتاً حاصل بازنکردن حساب‌های استفاده‌نشده است؛ با استفاده
از همهٔ حساب‌ها، RAM دوباره افزایش می‌یابد. همهٔ فایل‌های cookie و هفت profile
در تنظیمات باقی مانده‌اند؛ profileهای بازنشده وضعیت IDLE دارند.

اعتبارسنجی:

- ۱۳۸ تست Go و `go vet` موفق؛ race test دو package مرورگر نیز موفق.
- فلگ‌ها در command line واقعی هر هفت مرورگر بررسی شدند.
- پس از cleanup برای هر مرورگر فقط یک page target باقی ماند.
- پروفایل IDLE به نام chatgpt2 با reset داخلی در ۳۵٫۸ ثانیه HTTP 200 گرفت.
- صفحهٔ AI Studio و ChatGPT پیش‌فرض در health وضعیت READY گرفتند.
- ساخت توکن AI Studio انجام شد، اما تولید واقعی از upstream HTTP 403 گرفت؛
  پس از lazy startup نیز همین خطا تکرار شد.
- تست ChatGPT UI از upstream HTTP 200 دید، ولی adapter متن را استخراج نکرد
  و API HTTP 502 داد. یک تست direct نیز خطای UI HTTP 404 گرفت. سلامت کامل
  API تأیید نشده و صرفه‌جویی RAM به معنی حل این خطاها نیست.
